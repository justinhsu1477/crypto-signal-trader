# SaaS 架構設計理念（單一訊號源廣播）

> 產品北極星：不管 A/B/C/D 幾個用戶，全部都跟同一個 Discord 訊號源。

## 1. 核心定位

我們不是「多策略平台」，我們是「高品質 Discord 訊號同步跟單 SaaS」。

一句話版本：

`一個訊號源，統一解析，一鍵廣播，多用戶跟單。`

## 2. 產品最大賣點（必須持續被保留）

1. 訊號來源固定且清楚：來自平台管理的 Discord 訊號源。
2. 用戶不需要自己找訊號、不需要自己盯盤。
3. 同一筆訊號可同步覆蓋所有啟用自動跟單的用戶。
4. 用戶差異化只在風控參數，不在訊號來源。

## 3. 架構原則（不可動搖）

### 原則 A：單一訊號源
- 系統在同一時間只以「平台指定的 Discord 訊號源」為主訊號來源。
- 任何新功能都不能破壞「全用戶共享同一訊號源」這件事。

### 原則 B：解析一次，廣播多次
- 訊號只做一次解析，產生一份標準化交易意圖。
- 後端再將該交易意圖廣播給所有符合條件用戶執行。

### 原則 C：統一策略，個別風控
- 交易方向與時機由統一訊號決定。
- 每位用戶用自己的風控設定（倉位、風險比例、槓桿上限、DCA 層數）執行。

### 原則 D：非託管
- 每位用戶用自己的交易所 API Key 下單。
- 資金留在用戶自己的交易所帳戶，平台不託管資產。

### 原則 E：廣播失敗隔離
- 某位用戶下單失敗不能阻塞其他用戶。
- 廣播結果需按用戶分別記錄成功/失敗與原因。

### 原則 F：可觀測與可追溯
- 每一筆訊號都要能追到：
  - 原始 Discord 訊息
  - 解析結果
  - 廣播對象
  - 每位用戶實際執行結果

## 4. 標準資料流

```text
Discord 訊號源（唯一）
    -> Monitor 擷取訊息
    -> Signal Parser 解析成標準 TradeRequest
    -> BroadcastTradeService 廣播
    -> User A/B/C/D 各自用自己的 API Key 執行
    -> 分別通知 + 分別記錄
```

## 5. 產品邊界（刻意不做）

目前階段不以以下能力為主：

1. 多訊號源混合路由（多老師、多群組同時分流）
2. 每個用戶自選不同主訊號源
3. 用戶自建策略語言與複雜策略編排

原因：以上能力會稀釋當前最強賣點，並增加執行複雜度與維運風險。

## 6. 對內決策準則（每次開發都要問）

新功能若要上線，先問三件事：

1. 會不會弱化「同一訊號源、全用戶同步跟單」？
2. 會不會讓廣播鏈路變慢或更不穩？
3. 會不會降低風控與審計可追溯性？

只要任一答案是「會」，就應重新設計。

## 7. 對外溝通建議話術

對用戶：

`你只要完成 API Key 與風控設定，就能即時跟上同一個 Discord 訊號源。`

對團隊：

`我們的核心不是讓每個人有不同策略，而是把同一個高價值訊號穩定地複製到每個用戶帳戶。`
